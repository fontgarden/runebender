# Font engine benchmarks

Run the dependency-free benchmark harness from the repository root:

```sh
cargo bench --locked --no-default-features --bench font_engine
```

The `font_engine` Cargo bench target uses `harness = false`, `std::time::Instant`, and `std::hint::black_box` rather than a statistical benchmarking dependency.
The command uses Cargo's optimized bench profile and omits the application feature.
No external fonts, neighboring checkouts, network access at runtime, or environment variables are required.
Do not run other builds or benchmarks concurrently with it.

## Fixed workloads

The harness runs the small workload followed by the large workload, with 32 and 1,024 glyphs per source respectively.
Every glyph contains two closed contours (one rectangle and one two-segment cubic contour), ten points, and two named anchors.
Every eighth glyph after glyph zero also references glyph zero as a component, with no reference cycles.
Glyph positions and widths vary deterministically by glyph index.
The two interpolation masters share topology and vary outline positions, widths, anchor positions, and component translations along a single Weight axis.
Interpolation uses the fixed normalized location `0.375`, not a master location.
The load, save, import, and edit workloads use a single-source UFO with the same glyph population.

Each operation receives exactly three discarded warmups and fifteen measured samples, with no adaptive iteration counts or random input.
One sample performs one whole-font import, load, save, interpolation pass, or raw-file pass; an edit sample performs one guarded layer transaction, and a background sample performs one command or grouped history replay.
The harness prints the minimum, median, and nearest-rank 90th percentile in milliseconds per operation.
It also prints median microseconds per glyph, file, edit, or background command as appropriate.
Per-glyph interpolation time is the whole-font pass divided by the glyph count, not an independently sampled distribution of individual glyph latencies.
The printed file count and serialized byte count identify the disk workload generated by the current persistence implementation.

## Timing boundaries

| Operation | Included in the timed interval | Excluded setup |
| --- | --- | --- |
| `disk_read_files` | Read every serialized UFO file into newly allocated byte buffers, in sorted relative-path order. | Enumerating paths and allocating the outer result vector. |
| `disk_overwrite_files` | Overwrite every file in a separate, already populated UFO-shaped directory from captured byte buffers. | Capturing bytes, enumerating paths, creating directories, and initially populating files. |
| `canonical_import` | Consume a decoded `SourceInput` through the fallible `Project::from_source` canonical import boundary. | Synthetic font generation, cloning the decoded font, and creating the input wrapper. |
| `project_load_ufo` | Actual `Project::load` from an on-disk UFO, including filesystem access, parsing, validation, and canonical import. | Generating and initially saving the input UFO. |
| `project_save_ufo` | Actual `Project::save` to an existing UFO destination, including canonical export, serialization, staged filesystem publication, and marking the project saved. | Building a fresh project for each sample and initially populating the destination. |
| `interpolate_all_outlines` | Call `Project::interpolated_outline_at` for every glyph, including model evaluation, outline allocation, and recursive component resolution. | Building the two-master project, glyph-name list, location map, and outer result vector. |
| `edit_width_commit` | Begin a canonical layer transaction, set width to `725.5`, and commit a real change with document revision and history bookkeeping. | Importing a fresh single-source project and resolving the target layer's stable identity. |
| `edit_translate_commit` | Begin a canonical layer transaction, translate all ten points by `(1.25, -0.75)`, and commit a real change with document revision and history bookkeeping. | Importing a fresh single-source project and resolving the target layer's stable identity. |
| `background_copy` | Create the selected glyph's background and container, with one grouped history entry. | Importing the project and resolving the foreground address. |
| `background_copy_noop` | Repeat an identical copy, including semantic equality checks but no publication or history entry. | Importing the project and performing the first copy. |
| `background_swap` | Exchange different foreground/background contours as one group. | Importing, copying the background, and translating the foreground by `(10, -10)`. |
| `background_clear` / `background_clear_noop` | Clear an existing background or check an already absent one, respectively. | Importing and, for the changed case, copying the background. |
| `background_undo` / `background_redo` | Replay the copy group's exact layers and container through the common guarded history API. | Importing, copying, and, for Redo, undoing the group once. |

Both edit workloads target the glyph at the midpoint of the font's generated name range, which also contains a component.
The point translation deliberately leaves components and anchors unchanged, matching the canonical point-transform operation rather than a whole-glyph transform.
Every edit sample starts with fresh history and asserts that its transaction committed a change, so accumulating undo state and accidental no-ops do not skew later samples.
The transaction snapshot itself remains inside the timer because it is part of the public canonical edit operation.
Errors abort the benchmark instead of being counted as fast successful operations.

Background commands use the same midpoint glyph and source as the edit workloads.
Each sample starts from a fresh project with only the documented preparation, and asserts whether the named path changed or remained unchanged.
Returned invalidation data is retained until after the timer stops, as for ordinary edits.

The timer stops before destruction of returned values and setup-owned state.
Consequently, project teardown, retained interpolated outline teardown, and read-buffer teardown are excluded, while allocations and temporary-value destruction inside each engine call remain included.
Input construction and temporary-file cleanup are outside all measured intervals.

## Interpreting disk results

The two `disk_*` rows are explicit filesystem baselines, not font-engine benchmarks or equivalent replacements for transactional save.
They preserve the serialized file population but bypass directory traversal, parsing, serialization, validation, staged publication, and backup handling.
Do not subtract their timings from load or save timings to claim isolated CPU cost: their system-call sequences, allocation behavior, and cache interactions differ.
Use `canonical_import` and the other in-memory rows to distinguish engine work from end-to-end disk work.

All filesystem measurements are warm-cache observations after fixture creation and warmup.
The harness does not flush the operating-system page cache, request `fsync`, or claim crash-durable write latency.
Filesystem type, storage hardware, antivirus software, free space, and background activity can change results substantially.
Temporary files live under the operating system's temporary directory in a unique process-specific directory, which may be memory-backed on some hosts.
Normal completion explicitly removes that directory; an unwind also attempts cleanup and reports any cleanup error.
A forcibly terminated or aborted process can leave a `runebender-font-engine-bench-*` directory behind.

## Comparing revisions

Record the commit, `rustc -Vv`, operating system, CPU, memory, temporary-directory filesystem, and exact command alongside the complete output.
Use the same machine, toolchain, power mode, Cargo profile, and workload sizes for both revisions, and repeat complete runs to distinguish persistent changes from scheduling noise.
Compare small and large cases separately: a regression in document-size scaling can be hidden by a faster small-font result.
The fixed sample counts and reported percentiles are descriptive baselines, not confidence intervals or automatic regression thresholds.
No timing values are checked into this guide until they have actually been measured.

These synthetic workloads cover reusable engine entry points rather than GUI rendering, shaping, compilation, foreign-format import, variable-font saving, or the full complexity of production fonts.
Use focused correctness tests in addition to benchmarks; a lower latency is not evidence of preserved font semantics.

## Ownership cleanup completion target

This checklist bounds the hot-path ownership cleanup; it is not a claim that every font-engine operation has constant cost.
Explicit whole-document structural changes and isolated worker captures remain separate workloads.

- Ordinary layer edits and steady-state text paint do not create disposable whole-font snapshots or transformed copies of cached outlines.
- Background Copy, Swap, Clear and their Undo/Redo retain only the touched glyph layers, consulted foreground and any layer container created by the command.
  No-op commands retain no new history, do not advance the document revision, preserve existing identities and leave Redo usable.
- With target geometry, source/layer structure and actual component dependents held fixed, increasing unrelated glyphs from 32 to 1,024 does not increase background-command allocation requests or net retained Rust allocation bytes.
  Lookup/emptiness scans may still take longer; additional actual dependents and changed payloads are not unrelated work.
- Exact touched-layer, glyph-identity, layer-order and created-container guards reject conflicts before publication.
  Replay preserves unrelated glyph edits, refuses to remove a container adopted by another glyph, and restores exact source-format data through save/reopen.
- Focused history/preservation tests, strict native Clippy, the workspace suite, and browser build/interaction checks pass.

Use local allocation instrumentation alongside this harness to check cumulative allocation requests and net live requested bytes after dropping reply data.
Neither quantity is peak RSS or an allocator's usable-size measurement.
Timings remain machine-specific observations rather than a universal millisecond threshold.

### Local allocation evidence

Measured on 2026-11-13 in the ownership-cleanup working tree based on `2e4ddc0`, using Rust 1.96.1 (`31fca3adb`), macOS/Darwin 25.6 arm64, Apple M4 Pro and 48 GiB RAM.
The ordinary timing harness used `cargo bench --locked --no-default-features --bench font_engine`, with its temporary files under `/tmp` on `/dev/disk3s1s1`.
The allocation probe separately linked the optimized `--no-default-features` library and counted successful Rust allocation requests, including each reallocation's requested new size.
Its fixtures had 32 or 1,024 glyphs with one four-point rectangle and two anchors each, one source, no components and equal-length glyph names.
It dropped returned invalidation data before measuring net retained bytes, which include the published layer changes and retained history together, not history in isolation.

| Operation | Requested bytes, 32 glyphs | Requested bytes, 1,024 glyphs | Net retained bytes, 32 glyphs | Net retained bytes, 1,024 glyphs |
| --- | ---: | ---: | ---: | ---: |
| Copy, creating container | 16,849 | 16,849 | 15,467 | 15,467 |
| Identical Copy | 8,955 | 8,955 | 0 | 0 |
| Identical Swap | 12,586 | 12,586 | 0 | 0 |
| Changed Swap | 34,959 | 34,959 | 19,083 | 19,083 |
| Clear | 6,471 | 6,471 | 3,643 | 3,643 |
| Already absent Clear | 71 | 71 | 0 | 0 |
| Undo Clear | 10,947 | 10,947 | 2,591 | 2,591 |
| Redo Clear | 8,329 | 8,329 | -2,591 | -2,591 |

Changed Swap followed a foreground width edit; the timing harness instead swaps genuinely translated outlines.
The negative Redo Clear delta releases the live layer restored by Undo; it is not a negative allocation request or a reduction in the retained history group.
These measurements establish the fixed-payload scaling result, not a permanent CI memory threshold or a claim about total application RSS.

## Scaling with glyph count

Run the scaling harness to see whether an operation does more than linear work:

```sh
cargo bench --locked --no-default-features --bench large_font
```

It writes a two-master designspace at 1,000, 4,000 and 16,000 glyphs and times each operation once: open, one width edit on the first and on the last glyph, one interpolation, the snapshot for the preview compiler, and a save after editing one master.
Set `RUNEBENDER_BENCH_GLYPHS` to a comma-separated list of glyph counts to change the sizes.
Read the time per glyph across sizes: a figure that rises with the glyph count marks more than linear work.
Each operation runs once, so compare sizes within one run and do not treat a single figure as precise.

Measured on 2026-11-16 with Rust 1.96, macOS arm64, Apple M4 Pro, at 16,000 glyphs:

| Operation | Before | After |
| --- | ---: | ---: |
| Open designspace | 3,330 ms | 1,087 ms |
| Snapshot for preview compile | 318 ms | 61 ms |
| Save after editing one master | 6,965 ms | 2,228 ms |

Before, open and the snapshot looked up each glyph by scanning the glyph list, so their time per glyph rose with the glyph count; a name index removed that.
Save now skips masters without edits, writes an unchanged glyph file once, and stages masters in parallel.
Open also reads the masters of a designspace in parallel.
Reading the glyph files of one master on several threads was measured twice and was slower on this machine, so each master is still read on one thread.

## Layout tables

Run the benchmark of the live layout tables of the text line:

```sh
cargo bench --locked --no-default-features --bench layout_tables
```

It measures the repository fixtures `tests/fixtures/arabic` and `tests/fixtures/core`.
Set `RUNEBENDER_TEST_FONTS` to the Virtua Grotesk `sources` folder to measure Virtua Grotesk too.
Set `RUNEBENDER_AMIRI_DESIGNSPACE` to a designspace of Amiri to measure Amiri too.
An external font that does not load is reported and skipped.
The tables are built for one location without axes, so a feature file with variable values does not compile; such a font is measured without its feature file, and the output says so.

The inputs come from the first source of each font.
Each row has three discarded warmups and fifteen measured samples, and prints the minimum, the median and the nearest-rank 90th percentile.

| Row | Timed work |
| --- | --- |
| `LayoutInputs::from_project` | Read the advances, anchors, categories, kerning, groups and feature text of the source. |
| `cold build` | `LayoutTables::build` on a new builder: the first pass over the feature file, both feature writers, the compile and the shaping font. |
| `warm, one anchor change` | A rebuild after the first anchor of one glyph moves; the mark writer runs again. |
| `warm, one kerning change` | A rebuild after the first kerning value changes; the kerning writer runs again. |
| `warm, no change` | A rebuild with the same inputs; no writer runs, and the feature file is compiled again with the cached lookups. |
| `shape one line` | Shape one line of the script of the font with the built tables. |

Each change row changes the value by a different amount in each sample, so no build finds its value in the cache.
Copying the inputs for a change is outside the timer.
One edit of one line in the editor costs about the sum of `LayoutInputs::from_project`, one warm change row and `shape one line`.
Item 5.3 of [the Arabic text layout plan](ARABIC-TEXT-LAYOUT-PLAN.md) sets the budgets for that sum: 4 ms at 6,000 glyphs and 1 ms at 1,000 glyphs.

Measured on 2026-11-23 at `4d1eb56` with Rust 1.96.1, macOS arm64, Apple M4 Pro and 48 GiB RAM, medians in milliseconds.
Builds of other worktrees ran on the same host, so the figures are upper values.

| Row | Arabic fixture, 52 glyphs | Core fixture, 28 glyphs |
| --- | ---: | ---: |
| `LayoutInputs::from_project` | 0.015 | 0.006 |
| `cold build` | 0.496 | 0.101 |
| `warm, one anchor change` | 0.396 | 0.069 |
| `warm, one kerning change` | 0.301 | 0.075 |
| `warm, no change` | 0.195 | 0.039 |
| `shape one line` | 0.009 | 0.003 |

In the same run, a local Virtua Grotesk checkout with 914 glyphs, measured without its feature file, gave 0.49 ms to read the inputs, 6.9 ms for an anchor change, 3.6 ms for a kerning change and 2.8 ms with no change.
That is above the 1 ms budget of item 5.3, so items 5.1 and 5.2 are still necessary.

## Editor responsiveness

Run the optimized native point-drag probe without opening a window:

```sh
RUNEBENDER_TEST_FONTS=assets/font-sources/variable-fonts/VirtuaGrotesk \
cargo test --release --locked --features integration-fonts --bin runebender \
  frame_budget_report -- --ignored --nocapture --test-threads=1
```

The probe records input handling and scene construction separately over 240 point moves.
It compiles the preview font before the timed rebuilds, because the window compiles it on a worker thread, so the rebuild figures are the interface thread's own work.
Set `RUNEBENDER_BENCH_FONT` to a designspace or UFO to probe another font, and `RUNEBENDER_BENCH_GLYPH` to the glyph to open in it.
`RUNEBENDER_BENCH_KEEP=<folder>` makes the `large_font` benchmark leave its fixtures in that folder for this purpose.
`RUNEBENDER_BENCH_REPEAT=<count>` repeats the edit and its rebuild, so a sampling profiler attached to the test process sees that work.
With `RUNEBENDER_BENCH_OVERVIEW=1`, the same variable repeats a switch of master.
`RUNEBENDER_BENCH_TEXT=<text>` times the text line that the canvas reads on each paint: the placed sorts, the caret, the active origin and the kerning hit test.
The probe also prints the time of one pointer move with every point of the glyph selected, and the time of one copy of the session.

Measured on 2026-11-23 with the dev profile on the same machine, after the work of that day:

| Measurement | Before | After |
| --- | ---: | ---: |
| Repaint requests in a rebuild with no change in state | 40 | 0 |
| Layout requests in a rebuild with no change in state | 10 | 0 |
| Pointer move with all 264 points of `E009` selected | 252 us | 73 us |
| Switch of master, first visit, 919 glyphs and 8 masters | 15.7 ms | 7.9 ms |
| Switch of master, return to a visited master | 15.7 ms | 2.4 ms |
| Text line of 44 characters, placed sorts | not measured | 3.4 us |
| Rebuild of the overview with no change, 863 glyphs | 1.38 ms | 0.59 ms |
| Open a glyph from the overview, rebuild | 3.8 ms | 3.9 ms |

The text line is cheap, so its layout is not cached.
A profile of opening a glyph put 73% of the rebuild in Masonry: making the widgets of the editor and laying them out.
The application logic was 18%.
The time is not reduced, because it is the cost of replacing one large widget tree with another.
`RUNEBENDER_BENCH_OPEN=<count>` repeats the open and the close for a profiler.
A pen handle drag copies the layer transaction on each pointer move.
A copy of the whole session takes 100 us at 264 points, so that drag is left as it is.

Measured on 2026-11-17 with Rust 1.96, macOS arm64, Apple M4 Pro:

| Measurement | Virtua Grotesk, 863 glyphs | Synthetic, 16,000 glyphs |
| --- | ---: | ---: |
| Open in the application | 197 ms | 1,932 ms |
| Idle interface rebuild | 0.28 ms | 1.37 ms |
| Interface rebuild after an edit | 0.93 ms | 5.1 ms |
| Pointer move during a drag | 41 us | 40 us |
| Build one frame of the edit canvas | 139 us | 115 us |

Both fonts have two masters.
Before the work of 2026-11-16 and 2026-11-17, the rebuild after an edit took 4.0 ms on Virtua Grotesk and 83 ms at 16,000 glyphs.
Most of the 83 ms was reading the compiled preview font's glyph names one at a time, which costs glyphs squared.
It does not rasterize or present those scenes, so its paint measurements cannot establish native frame rate.
Its test-only preview compilation is synchronous; the native window compiles that preview on a worker.
Use `RUNEBENDER_FRAME_STATS=1` in an agreed native interactive session to observe display cadence, and use the browser checks in [web/README.md](../web/README.md) for browser input and rendering.
Browser `renderMs` excludes pointer handling before rendering and is not an input-to-display latency measurement.

### Frame times of a working session

Set `RUNEBENDER_FRAME_TIMES` to record the frame times of a window while a person works in it.
The recorder requests no frame and changes no pacing.
A value of `1` writes to stderr, and a path replaces that file.

```sh
RUNEBENDER_FRAME_TIMES=frame-times.log make run-release FONT=path/to/Font.designspace
```

The recorder writes one line for each second in which the window did work, with the mean and the worst case of each stage in milliseconds.
Each line ends with the open view, glyph and tool.

| Stage | Meaning |
| --- | --- |
| `interval` | The time between the starts of two consecutive redraws. A gap of 250 ms or more is idle time and is not counted. |
| `redraw` | One redraw: the Masonry paint pass, the Vello render, the wait for the next drawable of the display, and the present call. |
| `input` | The handling of one pointer, scroll or key event, with the application logic that it starts. |
| `logic` | One run of the application logic and the view rebuild. |
| `paint` | One paint of the editor canvas or of the glyph grid. It is part of a redraw. |
| `latency` | The time from the start of the newest input event of a frame to the end of the redraw that shows it. |

An `input`, `logic` or `paint` step of 8 ms or more, and a redraw of 50 ms or more, also gets a line of its own that starts with `slow`.
The footer shows the last second in short form, and it changes when the interface rebuilds.

Read the stages as follows.
A high `input`, `logic` or `paint` value is work of the editor on the interface thread.
A `redraw` near the refresh period of the display with low `paint` is the wait for the display, which the pinned Xilem does not report separately.
The `latency` value ends at the present call, so the compositor and the display add their own delay to it.

### Grid and initial-text follow-up

Local optimized probes on the same M4 Pro / 48 GiB host compared the layout helpers from `91f1ee0` with the cached implementation and compared incremental insertion with `TextBuffer::insert_characters`.
No builds or other benchmarks ran during these measurements.
Each case used three warmups and fifteen measured samples; the values below are medians, not frame-rate guarantees.

| Workload | Uncached or incremental | Cached or batched |
| --- | ---: | ---: |
| Grid geometry, 1,024 encoded cells | 0.033500 ms | 0.001417 ms |
| Grid geometry, 1,024 unencoded cells | 28.520000 ms | 0.001708 ms |
| Initial compiled text, 32 Latin characters | 0.509458 ms | 0.030708 ms |
| Initial compiled text, 128 Latin characters | 2.954750 ms | 0.051417 ms |
| Initial compiled text, 512 Latin characters | 37.300708 ms | 0.188375 ms |

The grid probe extracted the actual layout helpers into a standalone optimized Rust executable and exercised the paint path's geometry queries without drawing.
It used a 1000 × 700 viewport, 100-unit target cells, 8-unit insets, equal advances/aspect ratios, and captions without detail lines.
The cached measurements represent unchanged layout inputs; first layout, changed cells, caption/metric changes and resizing still repack the rows.
Encoding is determined once per layout, and the cache retains its cell identity so replacing cells cannot accidentally reuse an old key.

The text probe used the repository's Virtua Grotesk designspace and its compiled preview, with font compilation and inventory setup outside the timer.
Timed samples inserted repeated `a` characters and included shaping.
The probe also checked final sorts, layout and repeat-shaping stability for mixed Latin/Arabic, combining marks, ligatures and unmapped input.
The regression suite covers selection replacement, active-sort identity, fallback shaping, grid size changes, scrolling, and updated cell hit geometry.

The native drag probe after these changes recorded medians of 0.0458 ms for move handling and 0.1526 ms for scene construction on glyph `a` with 51 points.
The normal small-glyph drag was already fast; the large gains above address repeated grid layout and long initial text, not GPU rendering.
For a 60 Hz responsiveness target, measure complete frames during representative scrolling, dragging, zooming and long-text editing at Retina resolution.
Aim for p95 at or below 16.7 ms, inspect p99 stalls separately, and retain zero unnecessary idle repaints.
