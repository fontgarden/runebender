# Font engine benchmarks

Run the dependency-free benchmark harness from the repository root:

```sh
cargo bench --locked --no-default-features --bench font_engine
```

The `font_engine` Cargo bench target uses `harness = false`, `std::time::Instant`, and `std::hint::black_box` rather than a statistical benchmarking dependency.
The command uses Cargo's optimized bench profile and omits the application feature.
No external fonts, neighboring checkouts, network access at runtime, or environment variables are required.
Do not run other builds or benchmarks concurrently with it.

## Fixed workloads

The harness runs the small workload followed by the large workload, with 32 and 1,024 glyphs per source respectively.
Every glyph contains two closed contours (one rectangle and one two-segment cubic contour), ten points, and two named anchors.
Every eighth glyph after glyph zero also references glyph zero as a component, with no reference cycles.
Glyph positions and widths vary deterministically by glyph index.
The two interpolation masters share topology and vary outline positions, widths, anchor positions, and component translations along a single Weight axis.
Interpolation uses the fixed normalized location `0.375`, not a master location.
The load, save, import, and edit workloads use a single-source UFO with the same glyph population.

Each operation receives exactly three discarded warmups and fifteen measured samples, with no adaptive iteration counts or random input.
One sample performs one whole-font import, load, save, interpolation pass, or raw-file pass; an edit sample performs one guarded layer transaction, and a background sample performs one command or grouped history replay.
The harness prints the minimum, median, and nearest-rank 90th percentile in milliseconds per operation.
It also prints median microseconds per glyph, file, edit, or background command as appropriate.
Per-glyph interpolation time is the whole-font pass divided by the glyph count, not an independently sampled distribution of individual glyph latencies.
The printed file count and serialized byte count identify the disk workload generated by the current persistence implementation.

## Timing boundaries

| Operation | Included in the timed interval | Excluded setup |
| --- | --- | --- |
| `disk_read_files` | Read every serialized UFO file into newly allocated byte buffers, in sorted relative-path order. | Enumerating paths and allocating the outer result vector. |
| `disk_overwrite_files` | Overwrite every file in a separate, already populated UFO-shaped directory from captured byte buffers. | Capturing bytes, enumerating paths, creating directories, and initially populating files. |
| `canonical_import` | Consume a decoded `SourceInput` through the fallible `Project::from_source` canonical import boundary. | Synthetic font generation, cloning the decoded font, and creating the input wrapper. |
| `project_load_ufo` | Actual `Project::load` from an on-disk UFO, including filesystem access, parsing, validation, and canonical import. | Generating and initially saving the input UFO. |
| `project_save_ufo` | Actual `Project::save` to an existing UFO destination, including canonical export, serialization, staged filesystem publication, and marking the project saved. | Building a fresh project for each sample and initially populating the destination. |
| `interpolate_all_outlines` | Call `Project::interpolated_outline_at` for every glyph, including model evaluation, outline allocation, and recursive component resolution. | Building the two-master project, glyph-name list, location map, and outer result vector. |
| `edit_width_commit` | Begin a canonical layer transaction, set width to `725.5`, and commit a real change with document revision and history bookkeeping. | Importing a fresh single-source project and resolving the target layer's stable identity. |
| `edit_translate_commit` | Begin a canonical layer transaction, translate all ten points by `(1.25, -0.75)`, and commit a real change with document revision and history bookkeeping. | Importing a fresh single-source project and resolving the target layer's stable identity. |
| `background_copy` | Create the selected glyph's background and container, with one grouped history entry. | Importing the project and resolving the foreground address. |
| `background_copy_noop` | Repeat an identical copy, including semantic equality checks but no publication or history entry. | Importing the project and performing the first copy. |
| `background_swap` | Exchange different foreground/background contours as one group. | Importing, copying the background, and translating the foreground by `(10, -10)`. |
| `background_clear` / `background_clear_noop` | Clear an existing background or check an already absent one, respectively. | Importing and, for the changed case, copying the background. |
| `background_undo` / `background_redo` | Replay the copy group's exact layers and container through the common guarded history API. | Importing, copying, and, for Redo, undoing the group once. |

Both edit workloads target the glyph at the midpoint of the font's generated name range, which also contains a component.
The point translation deliberately leaves components and anchors unchanged, matching the canonical point-transform operation rather than a whole-glyph transform.
Every edit sample starts with fresh history and asserts that its transaction committed a change, so accumulating undo state and accidental no-ops do not skew later samples.
The transaction snapshot itself remains inside the timer because it is part of the public canonical edit operation.
Errors abort the benchmark instead of being counted as fast successful operations.

Background commands use the same midpoint glyph and source as the edit workloads.
Each sample starts from a fresh project with only the documented preparation, and asserts whether the named path changed or remained unchanged.
Returned invalidation data is retained until after the timer stops, as for ordinary edits.

The timer stops before destruction of returned values and setup-owned state.
Consequently, project teardown, retained interpolated outline teardown, and read-buffer teardown are excluded, while allocations and temporary-value destruction inside each engine call remain included.
Input construction and temporary-file cleanup are outside all measured intervals.

## Interpreting disk results

The two `disk_*` rows are explicit filesystem baselines, not font-engine benchmarks or equivalent replacements for transactional save.
They preserve the serialized file population but bypass directory traversal, parsing, serialization, validation, staged publication, and backup handling.
Do not subtract their timings from load or save timings to claim isolated CPU cost: their system-call sequences, allocation behavior, and cache interactions differ.
Use `canonical_import` and the other in-memory rows to distinguish engine work from end-to-end disk work.

All filesystem measurements are warm-cache observations after fixture creation and warmup.
The harness does not flush the operating-system page cache, request `fsync`, or claim crash-durable write latency.
Filesystem type, storage hardware, antivirus software, free space, and background activity can change results substantially.
Temporary files live under the operating system's temporary directory in a unique process-specific directory, which may be memory-backed on some hosts.
Normal completion explicitly removes that directory; an unwind also attempts cleanup and reports any cleanup error.
A forcibly terminated or aborted process can leave a `runebender-font-engine-bench-*` directory behind.

## Comparing revisions

Record the commit, `rustc -Vv`, operating system, CPU, memory, temporary-directory filesystem, and exact command alongside the complete output.
Use the same machine, toolchain, power mode, Cargo profile, and workload sizes for both revisions, and repeat complete runs to distinguish persistent changes from scheduling noise.
Compare small and large cases separately: a regression in document-size scaling can be hidden by a faster small-font result.
The fixed sample counts and reported percentiles are descriptive baselines, not confidence intervals or automatic regression thresholds.
No timing values are checked into this guide until they have actually been measured.

These synthetic workloads cover reusable engine entry points rather than GUI rendering, shaping, compilation, foreign-format import, variable-font saving, or the full complexity of production fonts.
Use focused correctness tests in addition to benchmarks; a lower latency is not evidence of preserved font semantics.

## Ownership cleanup completion target

This checklist bounds the hot-path ownership cleanup; it is not a claim that every font-engine operation has constant cost.
Explicit whole-document structural changes and isolated worker captures remain separate workloads.

- Ordinary layer edits and steady-state text paint do not create disposable whole-font snapshots or transformed copies of cached outlines.
- Background Copy, Swap, Clear and their Undo/Redo retain only the touched glyph layers, consulted foreground and any layer container created by the command.
  No-op commands retain no new history, do not advance the document revision, preserve existing identities and leave Redo usable.
- With target geometry, source/layer structure and actual component dependents held fixed, increasing unrelated glyphs from 32 to 1,024 does not increase background-command allocation requests or net retained Rust allocation bytes.
  Lookup/emptiness scans may still take longer; additional actual dependents and changed payloads are not unrelated work.
- Exact touched-layer, glyph-identity, layer-order and created-container guards reject conflicts before publication.
  Replay preserves unrelated glyph edits, refuses to remove a container adopted by another glyph, and restores exact source-format data through save/reopen.
- Focused history/preservation tests, strict native Clippy, the workspace suite, and browser build/interaction checks pass.

Use local allocation instrumentation alongside this harness to check cumulative allocation requests and net live requested bytes after dropping reply data.
Neither quantity is peak RSS or an allocator's usable-size measurement.
Timings remain machine-specific observations rather than a universal millisecond threshold.

### Local allocation evidence

Measured on 2026-11-13 in the ownership-cleanup working tree based on `2e4ddc0`, using Rust 1.96.1 (`31fca3adb`), macOS/Darwin 25.6 arm64, Apple M4 Pro and 48 GiB RAM.
The ordinary timing harness used `cargo bench --locked --no-default-features --bench font_engine`, with its temporary files under `/tmp` on `/dev/disk3s1s1`.
The allocation probe separately linked the optimized `--no-default-features` library and counted successful Rust allocation requests, including each reallocation's requested new size.
Its fixtures had 32 or 1,024 glyphs with one four-point rectangle and two anchors each, one source, no components and equal-length glyph names.
It dropped returned invalidation data before measuring net retained bytes, which include the published layer changes and retained history together, not history in isolation.

| Operation | Requested bytes, 32 glyphs | Requested bytes, 1,024 glyphs | Net retained bytes, 32 glyphs | Net retained bytes, 1,024 glyphs |
| --- | ---: | ---: | ---: | ---: |
| Copy, creating container | 16,849 | 16,849 | 15,467 | 15,467 |
| Identical Copy | 8,955 | 8,955 | 0 | 0 |
| Identical Swap | 12,586 | 12,586 | 0 | 0 |
| Changed Swap | 34,959 | 34,959 | 19,083 | 19,083 |
| Clear | 6,471 | 6,471 | 3,643 | 3,643 |
| Already absent Clear | 71 | 71 | 0 | 0 |
| Undo Clear | 10,947 | 10,947 | 2,591 | 2,591 |
| Redo Clear | 8,329 | 8,329 | -2,591 | -2,591 |

Changed Swap followed a foreground width edit; the timing harness instead swaps genuinely translated outlines.
The negative Redo Clear delta releases the live layer restored by Undo; it is not a negative allocation request or a reduction in the retained history group.
These measurements establish the fixed-payload scaling result, not a permanent CI memory threshold or a claim about total application RSS.
